## 一、开场一句话（30 秒版）

> 「一个安防场景的多模态 Agent：视觉检测 + 语音问答 + 工单流转 + MCP 工具暴露。
> 我在 8GB 显存的笔记本上把它跑通了，**全程不依赖 PyTorch**——

> 最有价值的不是功能，而是我在压测和指标上发现并修掉的 7 个真实缺陷，

**为什么这样开场**：面试官听腻了「我做了一个 XX 系统」。开场就给
「独立复现 + 零 torch + 7 个缺陷 + 数字可追溯」四个记忆点，且**主动划定边界**——
边界清晰比夸大功能更能建立信任。

## 二、架构（画图时按这个讲）

```
摄像头 / 图片
   └→ YOLO11n 目标检测 ── onnxruntime-gpu（CUDA）
        └→ InsightFace 人脸识别 ── onnxruntime-gpu
   语音输入 → faster-whisper ASR ── CTranslate2 (cpu-int8)
                    ↓
        Agent 编排（事件状态机 + 分层检索 RAG）
                    ↓
        MCP Server: query_events / create_ticket / stats
                    ↓
              SQLite 工单 + 统计看板
```

**分时加载**（8GB 显存的硬约束）：视觉模型、语音模型、LLM 不能同时常驻。
`ASRHandle.close()` 是刻意保留的设计——CTranslate2 会持有 CUDA 上下文，
不释放会和 YOLO 抢显存。

## 三、演示动线（建议 3 分钟，按这个顺序最有说服力）

### 第 1 步：先证明"真的在用 GPU"，而不是嘴上说

```bash
python scripts/demo_a_e2e.py
```

**开场第一句就要说**：
> 「这是实际生效的 provider，不是我读配置文件推断的——
> `['CUDAExecutionProvider', 'CPUExecutionProvider']`，未降级。」

> ⚠️ **这里有个坑值得主动讲**（面试加分项）：
> `get_available_providers()` 里有 CUDA **不代表 CUDA 真能用**。
> ONNX Runtime 缺 CUDA 依赖时**不抛异常，只是静默回退 CPU**，
> 而那份清单照样列出 CUDA，连 `get_device()` 都返回 GPU。
> 我第一次就踩了这个坑，误报过"CUDA 可用"。
> 所以我的判定标准是 `Session.get_providers()`——**实际绑定的结果**。

实测输出：

| 环节 | 实测值 |
|---|---|
| 视觉检测 | **约 7~8 ms**（实测 6.9~9.7 ms 波动；精确值见 `portal/measurements.json`；含预处理+NMS+坐标反算，不含模型首载）|
| 语音识别 | 真实中文语音 4.8 s → **约 1.37 s**（faster-whisper small / cpu-int8）|
| 语音识别准确率 | 整句正确 **6/12**，字符错误率 **0.1649** |
| RAG 检索 | 5~8 ms（bge-small-zh-v1.5 dim512 + FAISS）|
| 工单写入 | 幂等（同 id 连写两次仍 1 条）|

### 第 2 步：讲分层检索（这是最像"真做过"的部分）

问三个问题，现场跑：

```bash
# Q1 描述词提问 → 语义召回
"仓库门禁被暴力尝试的那条事件状态如何？"     → top-1 = A-0012（正确）

# Q2 结构化过滤 → 如实返回空
"东门有哪些未闭环的高危事件？"              → 0 命中（东门三条全已闭环）

# Q3 问句意图抽取
"摄像头 cam-01 记录了什么事件？"             → 自动抽出 camera_id 过滤
```

**核心讲法**（这段最能体现工程判断）：

> 「"东门未闭环"这个问题，正确答案就是**空**。
> 我的实现里，结构化候选为空时**如实返回空**，不会静默回退到全库。
> 因为一旦回退，回答就变成"我查了东门"但给的是西门的数据——
> 这比报错更危险。
>
> 而且我做过 A/B 对照：**声明了结构化过滤的 81 条题，准确率从 0.7778 升到 0.9506**。
> 这才是分层检索的价值所在，不是'我用了向量库'。」

### 第 3 步：主动交代未达标项

> 「简历写 94%，我实测 0.9118，**没到**。我不打算调参凑数。
> 差的这几条我查过：'门被撬了吗'命中了'翻越围栏'的工单而不是'暴力尝试'的——
> 这是语义近似的真实能力边界，不是判据问题。
> 证据是：**严格口径和宽松口径跑出来完全一样**（都是 0.9118），
> 说明不是判据宽松放过了错，是确实识别不出这个区分。」

## 四、可讲的工程决策（挑 2 个讲透，不要全讲）

### 决策 1：为什么不用 PyTorch

> 「我最初的计划就是装 torch cu128。实测本机带宽约 **343 KB/s**，
> torch + torchvision 约 2.7 GB，**要 137 分钟**。
> 但我核实了三个模型的依赖后发现：
> YOLO11n 有官方 ONNX（只 10.42 MiB）、InsightFace 本来就跑 ONNX、
> faster-whisper 用 CTranslate2。
> **三个都不需要 torch。** 于是全栈换成 ONNX + CTranslate2，总量约 500 MB。
>
> CUDA 运行时我是**只读复用** ComfyUI 那边 torch 自带的 CUDA 12.8，
> 用 `os.add_dll_directory` + `ort.preload_dlls()`，
> 没有复制也没有改动任何第三方文件。」

**这段的杀伤力**：体现了「先做技术调研再动手」，而不是"照着教程装依赖"。
而且**承认约束**（带宽慢）并给出解法，不是抱怨环境。

### 决策 2：压测方法本身也会骗人（强烈建议讲）

> 「我第一版压测是固定顺序、单轮采样。结果**同一份代码两次跑出 +28.2% 和 -9.2%
> 两个完全相反的结论**。
>
> 查下来是两个没控制的变量：① 固定'先 v1 后 v2'，高并发档的 v2 永远排在后面，
> 受前一轮热积累影响；② 单轮采样，而并发 16 时的 max 延迟高达 558ms，
> 尾部抖动被当成了典型值。
>
> 改成**每档 3 轮 + 轮内交替 v1/v2 顺序 + 取中位数**，再把'各轮 RPS 极差百分比'
> 作为可信度指标输出。修复后波动从 50%+ 降到 3~6%，结论才稳定。」

实测对照（3 轮取中位，26100 请求，失败 0）：

| 并发 | v1 RPS | v2 RPS | 提升 | 轮间波动 |
|---:|---:|---:|---:|---:|
| 1 | 213.32 | 260.61 | +22.2% | 3~6% |
| 4 | 419.40 | 522.19 | **+24.5%** | 3~6% |
| 8 | 432.56 | 479.74 | +10.9% | 3~6% |
| 16 | 300.86 | 316.91 | +5.3% | 3~6% |

> 「注意提升**不是越高越好**：并发 4 最高（+24.5%），并发 16 只有 +5.3%。
> 因为异步的收益来自'等待时间可重叠'，CPU 和线程池打满后就没有可重叠的等待了。
> 简历写 40%，我实测 +5.3%~+24.5%，**按实测报**。」

## 五、踩过的坑（挑 2 个，都是"不查日志就会得出错误结论"的类型）

### 坑 1：`check_same_thread=False` 不等于线程安全

> 「v2 用线程池做并发，一压就出 HTTP 500：
> `sqlite3.InterfaceError: bad parameter or other API misuse`。
> 并发 8 时失败 91 次，而 v1 零失败——**'优化后'比'优化前'更慢还更烂**。
>
> 根因是 `check_same_thread=False` **只解除'跨线程会抛异常'的检查，
> 不提供并发安全**。修法是每线程一个连接（`TicketStorePool`）。
>
> 有点讽刺：这个坑我第一版在 docstring 里就写明了正确做法，v2 还是违反了它。
> 所以我现在把'注释里的结论'也列进自检清单。」

### 坑 2：懒加载被算成了服务延迟

> 「`rag.load()` 首次 64 秒、之后 0.5 ms——差 13 万倍。
> 最初每个工作线程各自 load，8 个线程并发初始化互相争抢，
> 压测整体卡了 **4 分 36 秒**，而且第一个请求背上全部加载时间，读数直接失真。
>
> 改成用 FastAPI 的 `lifespan` 在启动时预热一次。
> 修复后同样并发 8 的压测从 **4 分 36 秒降到 2.2 秒，失败 0**。」

## 六、主动交代的局限（这部分千万别说"没有局限"）

| 局限 | 说明 |
|---|---|
| **ASR 用的是 TTS 合成语音** | 用 edge-tts 合成 12 条真人音色中文语音（带标准答案）。
> 合成语音信噪比高、无方言口音与背景噪声，**识别率系统性偏高**。
> 真人嘈杂场景**未测**——这是已知边界。|
| ASR 样本量小 | n=12，置信区间宽，只适合当回归护栏 |
| 口语短问识别差 | CER 0.352（「哪些事件是误报」被听成「每些世界十五包」）|
| 压测是本地回环 | 不含真实网络与数据库服务，RPS 绝对值不能与生产系统比 |
| 检索负载偏轻 | 仅 14 条工单，向量检索几乎瞬时；**大数据量下未验证** |
| 未接真实摄像头/工单平台 | 无生产数据 |

**收尾话术**：
> 「我把这些都写在文档的 gap_note 里，不藏。
> 尤其 ASR 那条——如果面试时我说'识别准确率 90%'，那是不诚实的，
> 因为我没在真人录音上测过。」
