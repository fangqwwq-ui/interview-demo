- v2 相对 v1 的 RPS 提升区间：**5.3% ~ 24.5%**（4 个并发档）

## 二、两版到底差在哪（唯一变量 = 并发模型）

| 维度 | v1（基线） | v2（优化后） |
|---|---|---|
| 端点类型 | 同步 `def`，阻塞工作线程 | 异步 `async def` + `run_in_executor` |
| SQLite 连接 | **每请求新建** `TicketStore` | **每线程一条**（`TicketStorePool`） |
| 索引/编码器 | 每请求重新 `load()` | 启动时预热一次，进程内常驻 |
| 数据/检索逻辑 | 完全相同 | 完全相同 |
| 机器/流量配比 | 完全相同 | 完全相同 |

**刻意保持不变的部分**：同一份 SQLite 库、同一套检索逻辑、同一台机器、同一流量配比。
变的只有并发模型这一项 —— 否则对比不成立。

## 六、过程中定位并修复的四个真实缺陷

前三个不是「调参」，是代码错误，都会表现为「v2 更慢或直接 500」——
如果不查日志只看最终数字，会得出完全错误的结论。第 4 个更隐蔽：**测量方法本身不可信**。

### 1. 单个 SQLite 连接被多线程并发使用 → HTTP 500

```
sqlite3.InterfaceError: bad parameter or other API misuse
```

- 现象：并发 8 时 v2 失败 91 次，而 v1 零失败。
- 根因：`check_same_thread=False` **只解除「跨线程抛异常」的检查，不提供并发安全**。
  把单个 `sqlite3.Connection` 共享给 8 线程的`ThreadPoolExecutor` 会随机崩。
- 修复：新增 `TicketStorePool`，每线程一条连接。

### 2. 懒加载被误算成服务延迟

```
rag.load()首次 ≈ 64241 ms，之后 ≈ 0.5 ms
```

- 现象：8 线程并发首档，整体卡 4 分 36 秒。
- 根因：每个工作线程各自 `load()`，并发触发 bge 模型初始化，互相争抢资源；
  且第一个请求会背上全部加载时间，压测读数失真。
- 修复：用 FastAPI `lifespan` 在启动时预热一次，之后请求只命中进程级缓存。
  实测并发 8 压测从**4 分 36 秒降到 2.2 秒，失败 0**。

### 3. 连接在错误线程里创建

```
IndexError: tuple index out of range / TypeError: 'NoneType' object is not subscriptable
```

- 现象：`/v2/stats` 在高并发下偶发 500。
- 根因：在事件循环线程里取好 store，再把 `store.stats` 丢进线程池 ——
  即「连接的创建线程」与「使用线程」不一致。
- 修复：把取连接的动作放进执行查询的那个函数内部（`_thread_store()` 在工作线程内调用）。

### 4. 压测本身不可信：固定顺序 + 单轮 → 结论可翻转

```
同一份代码，两次压测：+28.2% 与 -9.2%（结论相反）
并发16 时 stdev 50~60ms、max 558ms；改成交替顺序 + 3 轮中位数后 spread 1.6%~8.6%
```

- 现象：最初固定「先 v1 后 v2」且每档只跑一轮，结果不稳定到能自我矛盾。
- 根因：两个未控制的变量 ——
  ① **顺序偏差**：高并发档 v2 总排在 v1 之后，受到前一轮热积累影响；
  ② **单轮采样**：高并发下尾部抖动（max 558ms）被当成典型值。
- 修复：轮内交替 v1/v2 先后顺序；每档 3 轮取中位数；
  并输出 `rps_spread_pct` 作为**数据可信度指标**。

### 附带：线程池容量必须 ≥ 并发数

初版 `_POOL_SIZE=8` 而压测打到 16 并发，请求排队，v2 的 P95 反而比 v1 差
（239ms vs 167ms，**-18.9%**）。池是并发上限，池小于并发数时
「异步并发」退化为队列等待，拿不到任何收益。改为可配（默认 16）后转正。

## 七、局限与不可比之处（主动交代）

1. **单进程、无外部依赖**：本测试打的是本地 FastAPI，不含真实网络与数据库服务。
   RPS 绝对值不能与生产系统比较。
2. **未用 locust**：locust 依赖 gevent，本机带宽约 340 KB/s，
   为一个数字引入重依赖不划算。改用 httpx + asyncio 自建压测器，零新增依赖。
3. **检索负载偏轻**：Demo 语料仅 14 条工单，向量检索几乎瞬时。
   真实场景下索引加载与连接竞争的开销占比会更高，v2 优势可能更大 —— 
   但也可能因GIL 使CPU 密集段无法真正并行。**本测试不足以判断大数据量下的表现。**
4. **未压测写路径**：`create_ticket` 有写锁竞争，本次只压了读路径。
5. **提升幅度随机器与负载变化**：上表数字只在本机、本流量配比下成立。
