# Demo B 讲稿：AIGC 文案「AI 味」检测与改写

> **口径（开场就要说清）**：这是**方案的独立复现 / 技术验证版**。
> 检测内核是**第三方开源组件**（`humanize-chinese`，MIT），我做的不是内核，
> 而是**检测结果的可信度评估 + 自研词典 + 检索底座**。
> 改写臂目前只跑通了规则改写，LLM 改写通道因无 API Key 未实测。

---

## 一、开场一句话（30 秒版）

> 「这是一个 AIGC 文案质检工具。我的核心工作**不是造检测器**，
> 而是回答一个问题：**这个检测器到底能不能信？**
>
> 答案是：**分语域，而且我能量化它有多不可信**。
> 我发现它在种草腔上 4 条里有 3 条给 0 分——
> 也就是说这些文案它根本看不出来有 AI 味。
> 所以我做了第二套自研词典做交叉验证，并且**禁止把内核分当唯一指标**。」

**为什么这样开场**：绝大多数人会吹"我做了个检测器"。而"我证明了现有检测器在什么条件下失效，
并补了第二套仪器"是**更高一层的能力**——批判性思维 + 量化诚实。

---

## 二、架构

```
文案输入
   ├→ 第三方内核检测器（humanize-chinese, MIT）  ← detection-only，不改一行
   │     └→ 输出：AI 痕迹分 + 等级
   ├→ 自研词典 tells.py（可逐条指认）
   │     ├ 硬禁用表达 41 条（过渡套话 7 / 万能动词 6 / 空洞评价 16 / 营销话术 9 / 育儿套话 3）
   │     ├ 模板句式   10 条（正则，覆盖"留白填充"型句式）
   │     └ 软信号     5 条（仅提示，不计入）
   └→ 语义检索（bge-small-zh-v1.5 + FAISS）
         └→ 风格参考：35 篇人工撰写语料（5 垂类 × 7 篇）
```

**关键设计：双仪器并报，禁止合并总分**
两个通道量纲不同（第三方是打分，自研是命中计数），
合并成"综合合规分"没有物理意义且无法回归，所以**分开报**。

---

## 三、演示动线（建议 2.5 分钟）

### 第 1 步：先亮出"我发现的不可信"（这是全场最值钱的 30 秒）

打开 `bench/report.md` 或现场跑：

| 语域 | 条数 | 第三方内核均分 | 得 0 分条数 |
|---|---:|---:|---:|
| 公文腔 | 11 | 2.55 | 8 |
| 评测腔 | 4 | 3.00 | 2 |
| 种草腔 | 4 | **1.00** | **3** |
| 科普腔 | 1 | 0.00 | 1 |

**讲法**：

> 「种草腔 4 条里3 条得 0 分。如果我只报一个总均值 2.2→1，
> 看起来改写效果很好——但实际上这个仪器在种草腔上**基本失明**。
>
> 所以我做了两件事：① 报告**强制按语域分组**，禁止只给总均值；
> ② 用自研词典交叉验证，两套都报。」

### 第 2 步：讲改写效果（但强调这是**代理指标**）

实测（n=20，规则改写）：

| 指标 | 改写前 → 后 | 说明 |
|---|---|---|
| 第三方检测分 | 均值 **2.2 → 1** | 均降 1.2 分，**但中位数是 0.0** |
| 自研词典命中 | 均 **2.15 → 1.7 处** | 均减 0.45 处，合计减 9 处 |
| 语义保真度 | 均 **0.9831** | 改写没有破坏语义 |
| 新增语法异常 | **0 条** | 20 条里没有任何一条出现新语法错误 |

> ⚠️ **必须主动说的坑**：
> 「检测分**中位数是 0.0**，不是 1.0。也就是说**超过一半的样本改写前后都是 0 分**——
> 均值 1.2 的降幅听起来好，但那是少数高分样本拉起来的。
> 这个统计口径的差异，是我后来加不变量断言才发现的。」

### 第 3 步：讲一个我自己推翻的规则（极强加分项）

> 「我最初有条规则叫 R3'语气词 + 标点'。它在自己的样本上表现不错，
> 但我加了对照组之后发现——**它在完全正常的中文上大量误报**：
> '我们走吧。'、'太可了！' 都被判成语法异常。
>
> 这不是阈值没调好，是**规则定义本身就不成立**。
> 我把整条规则**直接删了**，而不是去收窄它。
> 历史指标全部按新规则集重算——R1/R2/R4，现在 20 条里 0 条误报。」

> **这段的杀伤力**：体现「敢于否定自己」+「用对照组暴露问题」+「不粉饰历史数据」。
> 绝大多数候选人不敢说自己删过自己的规则。

## 四、可讲的工程决策

补充一项支撑数据 —— **检索耗时**：中位数 **0.069 ms**、P95 **0.135 ms**
（60 次采样，后端 faiss-flat-ip，20 条查询 / 35 篇文档）。
⚠️ 口径边界：该数字**只含向量检索本身，不含向量化耗时**，
且仅在 Demo 规模（数十~数千条）下成立，十万条以上需换 IVF/HNSW 并重新标定召回。

### 决策 1：为什么不自己造检测器

> 「检测内核用的是第三方开源组件（MIT 协议），我**只用于检测、不改代码**。
> 理由很直接：造一个可靠的 AI 味检测器需要大规模标注数据，
> 我没有。而**评估现有检测器的边界**是我能做的事，也更有价值——
> 因为它直接决定了业务能不能用这个检测器。」

**必说**：第三方组件必须声明来源与协议，**严禁讲成自研**。
`detector.health()` 里就有provenance（仓库地址 + commit + MIT + `used_for: detection-only`）。

### 决策 2：编码器必须与建库时一致

> 「换编码器是个隐形陷阱：如果用 A 编码器建的库，换B 编码器去查，
> 相似度数值**毫无意义，但程序不会报错**——会静默产出垃圾结果。
> 所以我在 retriever 里做了硬拦截：编码器不一致直接抛异常，不给 warning。
> 因为 warning 会被忽略，而静默的错误结果会被当成正确答案用。」

### 决策 3：垂类过滤用"重排"而不是"过滤"

> 「向量库的契约我故意只做add/search，没有过滤器。
> 因为 Demo 语料每个垂类只有 7 条，一旦做硬过滤，top-3 可能凑不满。
> 所以用**超额召回 + 垂类优先 + 全局补齐**——
> 好处是永不返回空结果，而且我可以如实说明：
> **垂类字段是重排信号，不是硬约束**。」

## 五、踩过的坑（挑 2 个）

### 坑 1：用缓存/伪造的样本验证自己

> 「我最初用**自己造的测试文本**验证适配层，覆盖率 100%。
> 换成真实业务输入后——只剩 4~5 个词命中。
> **跑通≠ 可用。** 从那以后我定了一条规矩：
> 验证任何适配层，输入必须来自对方，不能自己造。」

这条在Demo C 也复现了同样问题（A/B 对照里扩词表才是真起作用的那一项）。

### 坑 2：跨工作负载平均

> 「我一开始把两种不同配置的结果平均：832×1216/28 步 与 512×512/4 步，
> 平均得25.7 秒。这个数字**不对应任何真实场景**——
> 两个配置的工作量根本不同。
> 所以现在我禁止跨工作负载平均，必须分档报告。」

## 六、主动交代的局限

| 局限 | 说明 |
|---|---|
| **检测器灵敏度分语域** | 种草腔 4 条中 3 条得 0 分；**必须与自研词典并报，不得单独引用** |
| 上游 README 分数不可复现 | 上游标注示例 72 分，本机实测 0 分；已在third_party/README.md 记录 |
| **改写臂只跑通规则改写** | LLM 改写通道无 API Key，**未实测，不给估算值** |
| 规则改写会破坏语法 | 实测「之于于」等病句（下游脚本会判 HIGH）→ 所以 LLM 改写才是正解 |
| 语料规模小 | 35 篇语料 / 20 条评测集，检索结论只在 Demo 规模成立 |
| 语义相似度 ≠ 质量 | 0.9831 只说明语义没丢，不说明文案变好了 |

## 七、可能的追问 → 见 `docs/objections.md`

1. 你怎么知道 0 分是真的没问题，还是检测器坏了？→ 交叉验证 + 分语域统计
2. 为什么不自己训模型？→ 没标注数据；评估边界比造检测器更可行
3. 51 个词典条目是不是拍脑袋？→ 分 6 类，每类可逐条指认（`tells.py` 导出）
4. 语义保真度 0.98 是怎么算的？→ bge 向量余弦，n=20，口径已登记
